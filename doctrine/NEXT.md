# What do I do next? The decision table

*Arriving at a project that did not start with this kit? If it has tests, audits or a history, read `RETROFIT.md` first:
the flags below can be derived read-only, and you do not have to install anything to use this table. A hook with no
tests and no history is a new project: phase 0, the code as the sketch to specify.*

The nine phases say what exists. This file says **when** each thing happens. Run it every time you arrive with no
context, and every time you finish anything. It is a table on purpose: you should be able to answer each condition
from `STATE.md` and the repository, without judgement calls. Where a judgement call is unavoidable, it says STOP.
`scripts/next.sh` computes the table from the flags; what it prints and refuses is at the end of this file and in
`state/README.md`. The table is the doctrine; the script follows it.

## The flags `STATE.md` must carry

Keep these lines at the top of `STATE.md`, and update them as part of closing any piece of work. They are
what makes the table computable.

```
phase:                     sketch | 0-8       (the phase that is OPEN; `3` means phase 3's gate is not met yet - write `4` the moment it is met, measured, `AGENTS.md` §3)
bytecode_changed_since:    last_battery=yes|no  last_long_fuzz=yes|no  last_other_free_judges=yes|no  last_audit_round=yes|no  last_promotion=yes|no|n/a
                           (last_battery and last_long_fuzz mean more: the INPUTS of that run changed - an edit under `src/`, under the suite's test directories (`test/`, the handlers; `pending/` too for the battery) or a compiler setting; a tests-only edit makes them `yes`. The others: bytecode, as below)
battery:                   never | green | red  (as of its last run; red = a failing, skipped or missing test)
blackbox:                  never_run | current | stale (promises, events or ABI changed since it ran) | skipped_by_owner (date) | stopped (<round id>)   (stopped: the environment stopped it twice, row 11b; it counts as spent)
open_findings:             high=N (<ids>) medium=N low=N reasoned_high_or_medium=N   (open = not yet fixed, refused in writing, accepted by the OWNER with a number, or handed to the human audit by name BY THE OWNER - the skeleton an agent writes lists findings, it hands nothing over; the ids of the open highs in the parentheses, no parentheses when N is 0; an id has at least one letter and one digit - `F-1`, `r01-A1`; `all`, `TBA`, `1` are not ids)
                           (a finding counts as REASONED only when it has NO test; one with a tested part and a reasoned part counts as tested, and the ROUND line's `reasoned` counts the same way; a REASONED one is one of the open high and medium, so `reasoned_high_or_medium` is never more than high + medium)
last_audit_round:          id, discovery | regression, result (e.g. r06 regression 0H 1M 3L)   - black-box and verifier rounds do NOT go here
last_other_round:          id, black-box | verifier, result
ceiling:                   not agreed (phase 0) | undecided | N model rounds ... agreed ...; M used | N model rounds, set by the operator (owner absent); M used   (reached when M >= N; what counts is below; the operator's form: `COST.md` §1)
real_manager_battery:      n/a (chain not chosen) | never | stale (bytecode changed since) | current
waiting_on_owner:          none | the questions, one per item, separated by `·` or `;`: triage of <ids> · high <id>[, <id>...] - to tell (row 1) · chain · RPC_URL for the real-manager battery (row 7b) · severity of <id> · reason for <judge> not run · read-back of scope · read-back of the spec · ...
location:                  .gauntlet/ | root       (where these files and the dossier live)
dossier:                   none | skeleton (K open, N judges not done) | complete (N judges not done)   (K = high + medium + low still open, informational NOT counted; `complete` means no finding is open - with one open the dossier is a skeleton)
rehearsal:                 n/a (no runbook) | not yet | done (YYYY-MM-DD)   (phase 7: a deployment runbook in the dossier, followed or not yet by an agent that did not write it)
notes:                     free lines the table reads by name at the START of a note item (a line, or a part after `·` or `;`; a list marker before it allowed): `static triage: forge lint only, Slither not installed` · `not fuzzable: <id> - <why>` · `real manager: <what replaced it>` (row 7b) · `fork: <answer or n/a - why>` · `pending: <id> - <promise>, owner undecided` (row 6b; several ids: `pending: F-4, F-5 - ...`)
```

A new project starts with: `phase: 0`, every `bytecode_changed_since` flag `yes` (nothing has run yet), `battery: never`,
`blackbox: never_run`, `open_findings` all 0, `last_audit_round: none`, `last_other_round: none`, `ceiling: not agreed
(phase 0)`, `real_manager_battery: n/a (chain not chosen)`, `waiting_on_owner: none`, `location:` as chosen, `dossier: none`,
`rehearsal: n/a (no runbook)`, `notes:` empty. `last_promotion` starts `n/a`, not `yes`: there was no promotion to change since.

"Bytecode changed" means anything that changes compiled output: an edit under `src/`, OR a compiler setting in
`foundry.toml` (`optimizer`, `optimizer_runs`, `via_ir`, `solc`, `evm_version`) of the profile the battery builds with.
A stranger measured a hook go from 1374 to 727 bytes with no edit under `src/`, from one `optimizer = true`; every flag
stayed `no`. The sandbox therefore lives in its own profile (`QUICKSTART.md` step 4), so that binding it never changes
the audited artefact. Comments change metadata, and therefore the deployed address, but not behaviour: they count for
promotion, not for rounds. **The battery's flag is wider: `last_battery` asks whether the battery's INPUTS changed** - an edit under `src/`, OR under
the suite's test directories (`test/`, the handlers wherever they live, `pending/`), OR a compiler setting as above. A
tests-only edit leaves the bytecode alone and still makes the last battery stale: its `02-test.txt` then cites a suite
that no longer exists (FR16: the handler edited after the battery, `last_battery` still `no`, and the round's auditor
found the report quoting the old run). So a test edit sets `last_battery=yes`, and row 6 runs the battery again. **The
long fuzz's flag follows the suite the same way: `last_long_fuzz` asks whether the long fuzz's INPUTS changed** - `src/`,
the test directories and the handlers it runs, a compiler setting. A handler edited after the long fuzz (FR16's, again)
means the campaign on record ran actions that no longer exist: `last_long_fuzz=yes`, and row 7 runs it again. The other
`bytecode_changed_since` flags keep the meaning above: bytecode.

## The table - take the FIRST row whose condition is true

Two rows are **gates, not stops**: 2 and 14. Look at them first. A gate whose condition is true turns off the rows it
names, wherever they stand, and the reading continues: the answer is the first row that is true and that no gate has
turned off. Row 2 (the ceiling is reached) turns off every model row: 11, 11b, 12, 13, 13b and 15. Row 14 (the loop is
over) turns off 11, 12, 13 and 13b - not 11b: a round the environment stopped, the closing black-box included, still
gets its one retry - and the reading continues below it, at row 15.

## The loops inside the table

- **Any bytecode change, at any phase, sends you back to row 6.** Including after promotion: a promoted artifact
  whose source changed is no longer promoted - reopen it on purpose, `CHANGES.md` section 4. Fix, battery, long fuzz, a diff-aimed round, then promote again.
  Expect this to happen at least once; the late rounds and the black-box exist to cause it.
- **A black-box divergence is fixed in the document or in the code.** If in the document, row 10 (verifier). If
  in the code, row 6.
- **The battery means both managers, once the chain is known.** From the moment the owner names the target chain,
  "the battery is green" includes a run against the real bytecode of that chain's pool manager
  (`scripts/fetch-bytecode.sh`, `V4_MANAGER=fixture scripts/battery.sh`). A suite that SKIPPED that path has not run it. Required
  before row 12 and before row 16.
- **What counts against the ceiling:** every model round - adversarial and black-box alike - counts as one. Verifier
  passes do not count, but they get a ROUND line in `LOG.md` like everything else. "Light mode: 3 rounds and a
  black-box" is a ceiling of 4.
- **If you take the same row twice in a row and nothing changed in between, or NO row is true, STOP.** You forgot to update a flag, or
  the table has a hole. Say which, in `STATE.md`, and ask - do not invent a flag change to get moving again. One STOP
  is not a hole: no row true, none left to judge, and `waiting_on_owner` not `none` is row 3's pause - the route's end
  with the owner absent. Say what is waiting, change nothing, and run the table again when they have answered. A reviewer
  found this table non-total once (light mode at its ceiling with a medium open had no row to phase 8); the fix was
  row 2, not a flag.
- **Ceremony check.** If the last hour of work produced no test run and no measurement - only state files, briefs
  and prose - stop and run one. The three state files exist so that work can be RESUMED, not so that they can be
  polished; an agent that spends its budget on them has walked the route without touching the code.
- **Rows 6-8 are local** - tools on the owner's machine, CPU time and nothing else. Rows 11-13 and 15 are run by a
  model and spend tokens. The table is ordered so that you never reach a model row while a local one is still true.

## Judgement calls the table cannot make for you

- **"Did the spec's promises change?"** Yes if a row of the hostile-actor table, an invariant, an admission rule
  or an event's meaning changed. No if only numbers, wording or examples did.
- **"Which places are trusted least?"** The orchestrator's call, written in the brief. Default: whatever the last
  fix touched, anything on the hot path that gained a branch, and the oldest accepted trade-off nobody has
  re-measured.
- **Which of two fixes?** Not a judgement call: build both and read the numbers. `CHANGES.md` section 2.
- **Fix the code or fix the sentence?** When the code does what was designed and the sentence promised more, fix
  the sentence. When the sentence is what the owner actually wants, fix the code - unless the owner is absent and the
  breach was found before round 1 (a phase-3 test under honest actions): then it is theirs to decide, row 6b's
  `pending/` path. If you cannot tell, that is an owner decision: row 3.

## How `scripts/next.sh` reads this table

The rows are data inside the script, one line per row, each keeping a hash of its condition cell above; a row in one
and not the other, another order, a condition reworded, or a malformed table line is a refusal naming the row
(`--check-table`). Before any row, the kit's own tools must be proven on this machine: `scripts/selftest.sh`, ending PASSED, leaves `<kit>/.gauntlet/selftest-passed` (the SHA-256 of the kit's scripts, a hash of this machine's identity, the date, the first line of `forge --version`); absent, with one of the three missing, or written for other scripts, on another machine or with another forge, `next.sh` prints only `next: FIRST - prove the kit on this machine: <kit>/scripts/selftest.sh (then run next.sh again) - <which>` (exit 0; `<which>` says the scripts, the machine or forge) - a property of the machine and the kit, not a flag of `STATE.md`. A kit copied to another machine with its `.gauntlet/`, or a project copied with the kit in `lib/hook-gauntlet`, starts with the selftest. The script refuses (exit 2) a flag it cannot read - missing, a value off its list, a malformed
line, a `dossier: complete` next to an open finding, a "to tell" item in any shape but the one above, an id recorded to
tell that is not an open high, a high count that does not match its ids - and a file in the project's `pending/` that no
`pending: <id>` note names, or an id of a `pending:` note with no file there (row 6b; no `pending/`, nothing checked).
Three more refusals come before any row (the local-model walk, judged 2026-09-30): a `STATE.md`, `DECISIONS.md` or `LOG.md` that is still the kit's
example - by its marker line, its title, or, for `STATE.md`, by its values: three or more of the example's
non-generic flag lines, whatever the spacing (`next: FIRST - fill STATE.md: ...`, no escape); a file in `pending/` with no
current, readable record of being seen red on `src/` as it stands (`scripts/pending-red.sh` writes it; escape
`PENDING_RED=0`); a file under the project that `STATE.md` or `DECISIONS.md` cites and that is not a non-empty regular
file - missing, empty or a directory (escape `CITED_FILES=0`; `LOG.md` is history and is not read for this) - each
escape said on stderr when it is set.
Every `.sol` file below `pending/` is read - subdirectories and hidden files too, as row 6b's profile compiles and runs
them all (forge 1.8.1, measured) - its id the file's name without `.t.sol` or `.sol`; a note may name several ids
(`pending: F-4, F-5 - ...`), and each needs its file. It prints the first true row and the flags that made it true (exit 0); a gate in
force is printed `in force`. What the flags cannot decide is asked, never guessed: rows 1 (a high open, not every one
recorded), 5, 8, 9, 9b, 10, 11b, 12, 16 and 18b are printed `needs judgement: row <id> - <question>` (exit 3) and
answered with `--judge <row>=true|false`, the answers echoed so the judgement is on the record (row 9b only while `dossier` is `none` or its K is not the number open: the question is then the owner's presence); row 3 is never
answered - it is decided by the flags, and the rows below that wait on the owner are answered false or turn
themselves off (7b). No row true and nothing waiting: `no row is true: the table has a hole or a flag is stale`
(exit 1). No row true, none to judge, and something waiting: `STOP - paused, waiting on the owner: <items>` (exit 0).
The details, and the ROUND line, are in `state/README.md`.
